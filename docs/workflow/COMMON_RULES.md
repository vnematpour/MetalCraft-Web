# قرارداد مشترک اسکیل‌های MetalCraft

## زبان و خروجی
- با کاربر فارسی صحبت کن؛ نام کلاس‌ها، APIها، فایل‌ها و شناسه‌ها را دقیق و انگلیسی نگه دار.
- اسناد فنی را Markdown بنویس.
- از اصطلاحات و ساختار واقعی پروژه استفاده کن؛ نام فایل، کلاس، فیلد یا رفتار را حدس نزن.
- خروجی هر مرحله باید فایل قابل‌ردیابی باشد، نه فقط توضیح در چت.
- هر ادعای مربوط به سورس باید مسیر فایل و در صورت امکان نام کلاس/متد/بخش را ذکر کند.
- هر تصمیم جدید باید در Decision Log ثبت شود.

## مرزبندی قطعیت
هر گزاره را با یکی از این برچسب‌ها مشخص کن:
- `CONFIRMED`: کاربر صریحاً تأیید کرده یا مستقیماً در منبع قابل اثبات است.
- `OBSERVED`: در سورس/دیتابیس مشاهده شده اما لزوماً قاعده محصول نیست.
- `PROPOSED`: پیشنهاد اسکیل است و نیاز به تأیید دارد.
- `OPEN`: اطلاعات کافی نیست یا تصمیم به تعویق افتاده است.

هیچ `PROPOSED` یا `OPEN` را به‌عنوان قانون قطعی پیاده‌سازی نکن.
اگر دو سند با هم تناقض دارند، تناقض را گزارش کن؛ خودسرانه یکی را انتخاب نکن. اولویت منبع:
1. پاسخ صریح و جدیدتر مالک محصول
2. تصمیم ثبت‌شده در `docs/decisions/`
3. مستندات نیازمندی تأییدشده
4. تحلیل سورس فعلی
5. پیشنهاد عمومی اسکیل

## مرز مسئولیت‌ها
- Product Owner نیاز و معیار پذیرش را تعیین می‌کند؛ معماری یا کد را انتخاب نمی‌کند مگر به‌عنوان محدودیت محصول.
- System Architect طراحی فنی و قراردادهای پیاده‌سازی را تعیین می‌کند؛ نیازمندی را بی‌اجازه تغییر نمی‌دهد.
- Developer فقط قرارداد تأییدشده را پیاده‌سازی می‌کند؛ سؤال باز را با حدس پر نمی‌کند.
- QA مستقل از پیاده‌سازی، معیارها و ریسک‌ها را راستی‌آزمایی می‌کند؛ کد را تغییر نمی‌دهد.
- هیچ اسکیلی خروجی اسکیل قبلی را بدون بررسی و ثبت ایراد، کورکورانه قبول نمی‌کند.

## اتمیک بودن Task
هر Task باید:
- یک نتیجه قابل مشاهده و محدود داشته باشد.
- در یک PR/commit یا تغییر منطقی قابل بازبینی تمام شود.
- معیار پذیرش مستقل و قابل آزمون داشته باشد.
- وابستگی‌هایش مشخص باشد.
- تغییرات نامرتبط را شامل نشود.
- اگر بیش از یک قابلیت مستقل دارد، به چند Task شکسته شود.

## شناسه و پوشه Task
شناسه یکتا مانند `MC-WEB-001` باشد.
برای هر Task پوشه زیر ایجاد شود:
`docs/workflow/tasks/<TASK-ID>/`

فایل‌های الزامی و ترتیب آن‌ها:
1. `00-task-brief.md` — خروجی Product Owner
2. `01-architecture.md` — خروجی System Architect
3. `02-implementation.md` — خروجی Developer
4. `03-qa-report.md` — خروجی QA
5. `04-acceptance.md` — خروجی نهایی Product Owner

فایل‌های مرحله بعد باید شناسه Task و نسخه/تاریخ ورودی مرحله قبل را ذکر کنند.

## Definition of Done مشترک
Task فقط وقتی Done است که:
- تمام معیارهای پذیرش بررسی شده باشند.
- تست‌های لازم اجرا شده و نتیجه واقعی ثبت شده باشد.
- هیچ تستی صرفاً به‌دلیل اجرا نشدن، Passed گزارش نشده باشد.
- QA وضعیت `PASS` داده باشد.
- Product Owner وضعیت `ACCEPTED` داده باشد.
- مستندات و Decision Log به‌روز باشند.
- تغییرات و محدودیت‌های باقی‌مانده ثبت شده باشند.

## ممنوعیت‌ها
- ساخت فیچر بدون Task تأییدشده ممنوع.
- افزودن پکیج، سرویس، الگوی معماری یا پیچیدگی غیرضروری بدون توجیه ممنوع.
- حذف داده/تغییر Schema بدون Migration و برنامه بازگشت ممنوع.
- تغییر رفتار فعلی صرفاً به دلیل سلیقه فنی ممنوع؛ تفاوت رفتار باید در Task ثبت و تأیید شود.
- ادعای اجرای تست، Build، Migration یا بررسی فایل بدون اجرای واقعی ممنوع.
- اطلاعات محرمانه، رمز، Connection String و داده شخصی واقعی را در مستندات/لاگ‌ها درج نکن.
